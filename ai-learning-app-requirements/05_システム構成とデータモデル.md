# 05 システム構成とデータモデル

[INDEXへ戻る](00_INDEX.md)

## 1. 配置方針

MVPはstandaloneデスクトップアプリとして動作します。UI、Application Core、Learning Orchestrator、Codex Gateway、Grounding Gateway、SQLite、Codex App Serverを同一端末内へ配置し、運営側のApplication API、BFF、PostgreSQL、Redisを必要としません。

外部通信はChatGPT認証、OpenAI／ChatGPTへのLLM通信、根拠資料のHTTPS読取り、明示同意した更新確認に限定します。

## 2. 論理コンポーネント

- Desktop Renderer: ログイン、ダッシュボード、教育課程・テーマ設定、計画、チャット・レッスン、演習、進捗、根拠資料、ノート・履歴を表示します。
- Application Core: typed IPC、入力検証、ローカル状態、処理の冪等性、エラー分類、SQLiteトランザクションを管理します。RendererからSQLite、認証情報、App Serverへ直接アクセスさせません。
- Learning Orchestrator: 計画生成、プロンプト構築、教育上の意味付け、教育課程原文から学習目標への変換候補、習熟度更新、補習経路、演習、採点、要約、Codexスレッド対応を管理します。
- Grounding Gateway: URL検査、根拠資料の検索・取得、取得制限、正規化、出典メタデータ、内容ハッシュ、キャッシュ、出典検証を管理します。
- Codex Gateway: App Server子プロセス管理、JSON-RPC、ID管理、イベント変換、タイムアウト、再起動・再接続、スキーマ検証を行います。
- Codex App Server: ChatGPT認証、Codex Thread・Turn・Item、OpenAI／ChatGPTとのストリーミング通信を管理します。
- ローカルデータストア: SQLiteとアプリ専用データディレクトリで構成します。ChatGPT認証とCodexネイティブ状態は、外部Codex CLIが既定またはユーザー設定済みの`CODEX_HOME`で管理します。

## 3. データの正本

| データ | 正本 |
|---|---|
| ローカルプロフィール、テーマ・目標、教育課程対応、計画、習熟度・進捗、補習経路、テスト・回答・採点、表示用会話履歴 | アプリDB（SQLite） |
| 根拠資料のURL、発行主体、版、取得時点、内容ハッシュ、引用対応 | アプリDB（SQLite） |
| 保存が許可された取得資料本文・スナップショット | アプリ専用データディレクトリ |
| ChatGPT認証情報 | Codex認証ストア（永続保存はOS資格情報ストア必須） |
| LLM処理中イベント | Codex App Server＋Application Coreの一時バッファ |
| Codexネイティブスレッド履歴 | 外部Codex CLIが所有する既定またはユーザー設定済み`CODEX_HOME` |

ChatGPT認証情報をアプリDBへ複製しません。Codexネイティブスレッドを削除・アーカイブしても、学習状態の確定データはアプリDBのライフサイクル規則に従います。

## 4. 主要データモデル

### LocalProfile
`id`, `display_name`, `locale`, `timezone`, `learning_preferences`, `created_at`, `updated_at`

MVPではOSユーザー単位の単一プロフィールです。ChatGPT認証情報やアクセストークンを保持しません。

### CurriculumProfile
`id`, `profile_key`, `country_code`, `jurisdiction_code`, `jurisdiction_name`, `jurisdiction_type`, `authority`, `official_name`, `selection_basis_city`, `selection_basis_type`, `selection_basis_rank`, `selection_basis_population`, `population_reference_date`, `selection_source_url`, `status`, `created_at`, `updated_at`

MVPの`profile_key`は`JP`、`US-DC`、`US-NY`、`US-CA`、`DE-BE`、`DE-HH`、`DE-BY`の安定キーとし一意制約を持ちます。`jurisdiction_type`は`national`、`state`、`land`、`federal_district`を区別します。`selection_basis_city`は対象管轄を選んだ根拠であり、教育課程の適用範囲そのものではありません。MVPの初期データは日本、コロンビア特別区、ニューヨーク州、カリフォルニア州、ベルリン州、ハンブルク州、バイエルン州の7教育管轄プロファイルに固定し、UAEの`AE`は初期データへ登録しません。

### Curriculum
`id`, `profile_id`, `official_name`, `official_code`, `authority`, `document_family`, `canonical_source_document_id`, `education_stage`, `grade_or_level`, `subject`, `version`, `effective_from`, `effective_to`, `language`, `status`, `created_at`, `updated_at`

1つの`CurriculumProfile`は、教育段階、学年、教科、版が異なる複数の`Curriculum`を持てます。人口統計の更新だけでは既存プロファイルを自動で置換しません。

### CurriculumItem
`id`, `curriculum_id`, `parent_id`, `code`, `title`, `description`, `prerequisite_item_ids`, `display_order`

### CurriculumObjective
`id`, `curriculum_item_id`, `official_code`, `original_text`, `language`, `source_snapshot_id`, `locator`, `display_order`

`CurriculumObjective`は教育課程資料に記載された個別の到達目標原文を保持します。学習計画で使用する目標は別の`LearningObjective`として`can_do`または`know`へ分類し、変換元を`LearningObjectiveCurriculumMapping`で追跡します。

### SourceDocument
`id`, `url`, `canonical_url`, `title`, `publisher`, `source_type`, `language`, `published_at`, `document_version`, `license`, `trust_level`, `retrieved_at`, `content_hash`, `retrieval_status`, `created_at`, `updated_at`

`source_type`は公的教育課程、教育機関資料、教科書・教材、補助資料、その他を区別します。

### SourceSnapshot
`id`, `source_document_id`, `retrieved_at`, `content_hash`, `storage_path`, `media_type`, `size_bytes`, `retention_policy`

資料本文を保存できない場合は`storage_path`を空とし、メタデータと内容ハッシュのみ保持します。

### CurriculumSourceMapping
`id`, `curriculum_item_id`, `source_document_id`, `relationship`, `evidence_range`, `verified_at`, `verification_status`

### LearningProject
`id`, `local_profile_id`, `mode`, `title`, `topic`, `purpose`, `curriculum_id`, `current_level`, `target_level`, `target_date`, `preferred_session_minutes`, `constraints`, `status`, `created_at`, `updated_at`

`mode`は`curriculum`または`free_topic`です。

`mode=curriculum`では、計画、学習目標、前提関係、概念、評価が参照する全`CurriculumItem`と`CurriculumObjective`が、`LearningProject.curriculum_id`と同一の`CurriculumProfile`に属することを不変条件とします。異なる管轄の参照を含むトランザクションは部分保存しません。

### LearningPlan
`id`, `project_id`, `version`, `status`, `generation_reason`, `generated_by_model`, `prompt_version`, `curriculum_version`, `created_at`

### LearningObjective
`id`, `project_id`, `current_version_id`, `lifecycle_status`, `created_at`, `updated_at`

`LearningObjective`は学習目標の論理IDと現在版を管理します。`lifecycle_status`は目標定義の有効・失効を示し、学習者の達成状態を保持しません。

### LearningObjectiveVersion
`id`, `learning_objective_id`, `version_number`, `plan_id`, `module_id`, `lesson_id`, `scope`, `goal_type`, `statement`, `target`, `conditions`, `success_criteria`, `evidence_method`, `curriculum_item_ids`, `source_document_ids`, `display_order`, `created_at`

目標定義はappend-onlyとし、編集時は既存行を上書きせず新しい`LearningObjectiveVersion`を作成して`current_version_id`を更新します。`scope`は`project`、`module`、`lesson`、`goal_type`は`can_do`または`know`です。`scope=project`では`plan_id`、`module_id`、`lesson_id`をNULL、`scope=module`では`plan_id`と`module_id`を必須かつ`lesson_id`をNULL、`scope=lesson`では3つ全てを必須とするCHECK制約を適用します。参照する計画、モジュール、レッスンは同一`project_id`に属する必要があります。`goal_type`を判別キーとするdiscriminated unionとして扱い、両種類とも目標文、対象、条件、成功基準、評価方法を必須とし、空文字・空白のみ・未知フィールドを拒否します。`can_do`は観測可能な行動、`know`は説明、区別、関連付け、理由提示などで確認する評価方法を保持します。

### LearningObjectiveCurriculumMapping
`id`, `learning_objective_version_id`, `curriculum_objective_id`, `transformation_version`, `verification_status`, `verified_at`

### ObjectiveEvidence
`id`, `objective_id`, `learning_objective_version_id`, `evidence_type`, `assessment_attempt_id`, `result`, `score`, `success_criteria_snapshot`, `rubric_version`, `evaluator_model`, `prompt_version`, `accepted_for_attainment`, `rejection_reason`, `verified_at`, `created_at`

`evidence_type`は`diagnostic`、`practice`、`lesson_check`、`final_check`、`self_assessment`です。MVPでは全ての証拠が`AssessmentAttempt`を参照し、対応する`Assessment.type`と`evidence_type`の一致、および`learning_objective_version_id`が当該`Assessment.learning_objective_version_ids`に含まれることを検証します。証拠が同じ学習者、プロジェクト、目標版に属し、成功基準を満たすことをApplication Coreがトランザクション内で検証します。自己評価は保存できますが、単独の場合は`accepted_for_attainment=false`、`rejection_reason=SELF_REPORT_ONLY`とします。空証拠、削除済み証拠、別目標の証拠、LLMが参照だけで生成した証拠、曖昧な採点は達成証拠として採用しません。

### ObjectiveAttainment
`id`, `local_profile_id`, `project_id`, `objective_id`, `learning_objective_version_id`, `status`, `evidence_ids`, `evaluated_at`, `invalidated_at`, `invalidation_reason`

`status`は`not_started`、`in_progress`、`needs_review`、`achieved`、`invalidated`です。達成状態はApplication Coreだけが算出します。目標定義、成功基準、証拠、ルーブリック、採点結果の変更・削除・再評価時は旧判定を失効または再計算し、RendererとLLMからの達成状態の直接設定を拒否します。

### PlanModule／Lesson
`id`, `plan_id`, `parent_id`, `key`, `title`, `description`, `learning_objective_ids`, `prerequisite_ids`, `curriculum_item_ids`, `source_document_ids`, `estimated_minutes`, `display_order`, `status`

### RemediationPath
`id`, `project_id`, `trigger_concept_id`, `origin_lesson_id`, `remediation_lesson_ids`, `return_conditions`, `status`, `started_at`, `completed_at`

### Concept
`id`, `project_id`, `name`, `description`, `curriculum_item_ids`, `prerequisite_concept_ids`, `importance`

### ConceptMastery
`id`, `local_profile_id`, `project_id`, `concept_id`, `status`, `mastery_score`, `confidence`, `evidence_item_ids`, `last_evaluated_at`, `next_review_at`

### LearningSession
`id`, `project_id`, `lesson_id`, `active_thread_id`, `started_at`, `last_resumed_at`, `ended_at`, `status`, `summary`, `next_action`

1件のLearningProjectは複数LearningSessionを持ちます。1件のLearningSessionは通常1件のThreadで
複数Turnを継続しますが、Fork時は複数Threadを持ちます。同一Thread再開時はLearningSession IDを維持します。

### CodexThread
`id`, `session_id`, `project_id`, `codex_thread_id`, `parent_thread_id`, `forked_from_item_id`, `fork_mode`, `status`, `created_at`, `last_resumed_at`

### CodexTurn
`id`, `thread_id`, `session_id`, `project_id`, `codex_turn_id`, `request_id`, `input_text`, `status`, `started_at`, `completed_at`

### CodexOperation
`id`, `request_id`, `kind`, `entity_id`, `state`, `error_code`, `created_at`, `updated_at`

外部I/Oの前に意図を確定し、I/O後の別トランザクションで結果を反映するために使用します。

### Message／LLMItem
`id`, `session_id`, `thread_id`, `turn_id`, `codex_thread_id`, `codex_turn_id`, `codex_item_id`, `role`, `item_type`, `content`, `source_citation_ids`, `sequence`, `provider_order`, `status`, `created_at`

`sequence`は追記時に確定する不変の履歴cursorです。`provider_order`はCodex Thread内の正規順序であり、
reconciliationで過去の欠落Itemを発見した場合も既発行cursorを再採番せず、Thread表示とFork prefixを正規順序へ戻します。

### SourceCitation
`id`, `source_document_id`, `snapshot_id`, `locator`, `quoted_text_hash`, `claim_type`, `verification_status`, `created_at`

### Note
`id`, `local_profile_id`, `project_id`, `lesson_id`, `concept_id`, `content`, `source_document_ids`, `curriculum_item_ids`, `created_at`, `updated_at`

### Bookmark
`id`, `local_profile_id`, `project_id`, `lesson_id`, `concept_id`, `message_id`, `note`, `source_document_ids`, `curriculum_item_ids`, `created_at`

### Assessment
`id`, `project_id`, `lesson_id`, `type`, `difficulty`, `learning_objective_version_ids`, `curriculum_item_ids`, `source_document_ids`, `schema_version`, `created_at`

`type`は`diagnostic`、`practice`、`lesson_check`、`final_check`です。問題生成時点の不変な`LearningObjectiveVersion`を保持します。初期診断も`Assessment`と`AssessmentAttempt`で表現し、`type=diagnostic`では`lesson_id`をNULLにできます。それ以外では対象レッスンまたは最終確認対象を契約で指定します。

### AssessmentAttempt
`id`, `assessment_id`, `local_profile_id`, `answer`, `score`, `evaluation`, `rubric`, `hint_count`, `started_at`, `submitted_at`

### LLMRun
`id`, `local_profile_id`, `project_id`, `purpose`, `model`, `prompt_version`, `curriculum_version`, `source_document_ids`, `input_size`, `output_size`, `latency_ms`, `status`, `error_code`, `created_at`

## 5. 削除・保持境界

- ChatGPTログアウトはCodex認証情報を削除しますが、端末内学習データを削除しません。
- ローカルプロフィール削除はアプリDB、保存済み根拠資料、対応Codexスレッドを削除対象とします。アーカイブは削除と別の操作・結果として扱います。
- 個別テーマ削除は関連する計画、進捗、評価、履歴、引用対応を削除します。複数テーマで共有する根拠資料は参照が残る限り保持できます。
- アプリのアンインストールだけでOS資格情報ストアやデータディレクトリが必ず削除されるとは仮定せず、アプリ内に明示的な全データ削除操作を提供します。全データ削除はSQLite本体・WAL、保存資料・スナップショット、Codex状態、資格情報、キャッシュ、ログ、下書き、一時ファイルを対象別に処理します。部分失敗時は完了表示せず、対象別結果を保持して再試行可能にし、処理後に孤児参照と資格情報残存を検査します。
